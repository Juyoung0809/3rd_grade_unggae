## BUG-001: 유료 강의 수강신청 시 결제 페이지로 이동하지 않는 문제

### 발생일
2026-06-11

### 증상
유료 강의 상세 페이지에서 "수강신청" 버튼을 클릭하면 결제 페이지로 이동하지 않고,
"유료 강의는 결제 후 수강신청이 가능합니다" 라는 alert 팝업만 뜨고 그대로 멈춤.

### 원인
`Front/src/pages/CourseDetailPage.tsx`의 `handleEnroll()`이 강의 가격과 무관하게
`enroll()` API(`/api/enrollments`)를 직접 호출하고 있었음. 백엔드의
`EnrollmentService.enroll()`은 `course.getPrice() > 0`이면 `PAYMENT_REQUIRED` 에러를 던지므로,
프론트는 이 에러 메시지를 alert으로만 띄우고 결제 흐름으로 연결하지 않았음.

### 수정 내용
`handleEnroll()`에서 `course.price > 0`인 경우 `enroll()`을 호출하지 않고
`/payment/:courseId`(결제 페이지)로 라우팅하도록 분기 추가. 무료 강의는 기존처럼
`enroll()`을 직접 호출하여 즉시 수강 등록되도록 유지.

- `Front/src/pages/CourseDetailPage.tsx` — `handleEnroll()` 수정

### 검증
유료 강의 상세 페이지에서 "수강신청" 클릭 시 `/payment/:courseId`로 정상 이동하는 것을 확인.

## BUG-002: 결제 진행 시 /api/payments/prepare 500 서버 오류

### 발생일
2026-06-11

### 증상
결제 페이지에서 "결제하기"를 누르면 `POST /api/payments/prepare` 호출이
`500 INTERNAL_SERVER_ERROR` ("서버 오류가 발생했습니다.")를 반환하며 결제가 진행되지 않음.

### 원인
DB의 `payments` 테이블 스키마가 `Payment` 엔티티 정의와 어긋나 있었음
(과거 설계 당시 만든 테이블이 엔티티 변경 후 마이그레이션되지 않음, `ddl-auto: update`는
컬럼 타입/ENUM 값/NOT NULL 변경이나 컬럼 추가를 자동으로 반영하지 못함).

- `method` ENUM이 `('CARD','FREE')`로 되어 있었으나 엔티티는 `FREE`/`TOSS` 값을 기대
- `status` ENUM이 `('COMPLETED','REFUNDED')`로 되어 있었으나 엔티티는
  `PENDING`/`COMPLETED`/`FAILED`/`REFUNDED` 값을 기대
- `paid_at` 컬럼이 `NOT NULL`이었으나, `PENDING` 상태의 결제는 `paidAt`이 `null`이어야 함
- `created_at` 컬럼이 테이블에 아예 존재하지 않음
  (엔티티는 `@Column(name = "created_at", nullable = false)` 필수)

### 수정 내용
운영 DB(`unggae` 스키마)의 `payments` 테이블에 직접 SQL 마이그레이션 적용.

```sql
-- ENUM 확장 후 기존 데이터 변환, 다시 축소
ALTER TABLE payments MODIFY COLUMN method ENUM('CARD','FREE','TOSS') NOT NULL;
ALTER TABLE payments MODIFY COLUMN status ENUM('PENDING','COMPLETED','FAILED','REFUNDED') NOT NULL;
ALTER TABLE payments MODIFY COLUMN paid_at DATETIME(6) NULL;
UPDATE payments SET method = 'TOSS' WHERE method = 'CARD';
ALTER TABLE payments MODIFY COLUMN method ENUM('FREE','TOSS') NOT NULL;

-- created_at 컬럼 추가 및 백필
ALTER TABLE payments ADD COLUMN created_at DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6);
UPDATE payments SET created_at = paid_at WHERE paid_at IS NOT NULL;
```

### 검증
`@SpringBootTest` 기반 임시 디버그 테스트와 curl을 통해
`prepare` → `mock-confirm` → `my-payments` → `my-enrollments` 흐름을 모두 200 OK로 확인.
결제 완료 시 `Enrollment`가 정상 생성되고 결제 내역 조회도 정상 동작함을 검증 후,
테스트 데이터 및 임시 디버그 테스트 파일은 모두 삭제함.

## BUG-003: 결제 요청 실패 시 백엔드 로그에 아무 기록도 남지 않는 문제

### 발생일
2026-06-11

### 증상
결제 모달에서 "다음"을 눌러 결제를 진행하면 "결제 중 오류가 발생했습니다."
(프론트엔드의 일반 fallback 메시지)만 표시됨. 그런데 `Back/logs/unggae.log`에는
`/api/payments/*` 요청이 단 한 건도 기록되지 않아, 요청이 실패하는 지점을
특정할 수 없었음.

### 원인
`RequestLoggingFilter`가 `@Order(1)`로 등록되어 있었는데, Spring Security의
`FilterChainProxy`는 `Ordered.HIGHEST_PRECEDENCE + 100` (훨씬 낮은 값 = 더 먼저 실행)
순서로 등록되어 항상 먼저 실행됨. `/api/payments/**`는 `anyRequest().authenticated()`
규칙에 걸리는데, 액세스 토큰이 없거나 만료된 상태로 요청하면 Spring Security가
`AuthorizationFilter` 단계에서 401/403으로 즉시 응답을 커밋해버리고, 그 뒤에 있는
`RequestLoggingFilter`까지 요청이 도달하지 못해 아무 로그도 남지 않았음.

또한 이때 응답 바디가 `ApiResponse` JSON 형식이 아니라 비어 있어서, 프론트엔드의
`err.response?.data?.message`가 `undefined`가 되어 항상 일반 fallback 메시지
("결제 중 오류가 발생했습니다.")만 표시되었음.

### 수정 내용
- `Back/src/main/java/juyoung/unggae/common/filter/RequestLoggingFilter.java`
  — `@Order(1)` → `@Order(Ordered.HIGHEST_PRECEDENCE)`로 변경하여 Spring Security
  필터 체인보다 먼저 실행되도록 수정. 이제 인증 실패로 거부된 요청도 `[REQ]`/`[RES]`
  로그(상태코드 포함)가 남음.
- `Back/src/main/java/juyoung/unggae/common/security/SecurityResponseHandler.java` (신규)
  — `AuthenticationEntryPoint`/`AccessDeniedHandler` 구현체 추가. 인증/인가 실패 시
  WARN 로그를 남기고, `ApiResponse` 형식의 JSON(`{"code":"UNAUTHORIZED", "message":"로그인이 필요합니다.", "data":null}` 등)을
  401/403 상태코드와 함께 반환.
- `Back/src/main/java/juyoung/unggae/common/security/SecurityConfig.java`
  — `.exceptionHandling()`에 `SecurityResponseHandler`를 `authenticationEntryPoint`/
  `accessDeniedHandler`로 등록.
- `Back/src/main/java/juyoung/unggae/common/response/ErrorCode.java`
  — `UNAUTHORIZED`(401, "로그인이 필요합니다."), `FORBIDDEN`(403, "접근 권한이 없습니다.") 추가.

### 검증
백엔드 재시작 후, 토큰 없이 `curl -X POST /api/payments/prepare`로 호출하여
- 응답: `401 {"code":"UNAUTHORIZED","message":"로그인이 필요합니다.","data":null}`
- `unggae.log`에 `[REQ] POST /api/payments/prepare` → `[WARN] 인증 실패 (401)` →
  `[RES] POST /api/payments/prepare → 401`이 모두 기록됨을 확인.

이제 결제 요청이 실패하면 (1) 백엔드 로그에 항상 추적 가능한 기록이 남고,
(2) 토큰 만료/누락 시 프론트엔드에 "로그인이 필요합니다."라는 명확한 메시지가
표시되어, 일반 fallback 메시지로 원인을 알 수 없던 문제가 해결됨.

## BUG-004: 강의 목록 "수강생순" 정렬이 실제 수강생 수가 아닌 레슨 개수 기준으로 동작하는 문제

### 발생일
2026-06-12

### 증상
강의 목록 페이지에서 정렬을 "수강생순"으로 선택해도, 실제 수강신청(Enrollment) 건수와
무관하게 강의에 등록된 레슨(챕터) 개수가 많은 순서로 정렬됨. COURSE-06 요구사항은
"정렬(최신순/평점순/수강생순)"을 명시하고 있어, 수강생순은 실제 수강 인원 기준이어야 함.

### 원인
`Back/src/main/java/juyoung/unggae/course/service/CourseService.java`의 `getCourses()`에서
`STUDENTS` 정렬 시 `CourseResponse.getLectureCount()`(레슨 개수)를 기준으로
`responses.sort()`를 수행하고 있었음. `CourseResponse`에는 실제 수강생 수를 담는 필드가
존재하지 않았고, `EnrollmentRepository`에도 강의별 활성 수강 건수를 세는 메서드가 없었음.

### 수정 내용

- `Back/.../course/dto/CourseResponse.java` — `enrollmentCount` 필드 추가, `of(course, averageRating, enrollmentCount)`로 시그니처 변경
- `Back/.../course/service/CourseService.java` — `STUDENTS` 정렬 기준을 `getLectureCount()` → `getEnrollmentCount()`로 변경
- `Back/.../admin/service/AdminCourseService.java` — `CourseResponse.of()` 호출부에 `enrollmentCount` 전달
- `Front/src/api/courses.ts` — `Course.enrollmentCount` 필드 추가
- `Front/src/pages/CourseListPage.tsx` — 강의 카드에 "수강생 N명" 표시 추가하여 정렬 결과를 시각적으로 확인 가능하도록 함

### 검증
백엔드 컴파일(`./gradlew compileJava`) 및 프론트엔드 타입 점검(`tsc --noEmit`) 통과 확인.
강의 목록에서 "수강생순" 선택 시 `enrollmentCount` 내림차순으로 정렬되고, 각 카드에
표시되는 "수강생 N명" 값이 정렬 순서와 일치하는지 확인.

## BUG-005: 유튜브(YouTube) 강의 시청 완료 시 진도율이 갱신되지 않는 문제

### 발생일
2026-06-13

### 증상
유튜브 영상으로 등록된 강의를 끝까지 재생해도 "수강 완료" 처리가 되지 않고,
진도율(`progressPercent`)과 완료 강의 수(`completedLectureCount`)가 전혀 변하지 않음.
(업로드형(UPLOAD) 영상은 정상 동작)

### 원인
`Front/src/pages/LessonPlayerPage.tsx`에서 유튜브 iframe src에 `enablejsapi=1`만 추가하고,
영상 종료를 감지하기 위해 `window.addEventListener('message', ...)`로
`onStateChange`/`infoDelivery` 이벤트를 직접 파싱하려 했음. 그러나 정식 YouTube
IFrame Player API(`https://www.youtube.com/iframe_api` 스크립트 로드 + `new YT.Player(...)`
생성)로 postMessage 브릿지를 초기화하지 않으면, iframe은 해당 이벤트를 부모 창으로
전달하지 않음. 결과적으로 영상이 끝나도 `onStateChange` 이벤트가 전혀 수신되지 않아
`handleVideoEndedRef`가 호출되지 않고, `POST /api/enrollments/{courseId}/complete-lecture/{lectureId}`가
호출되지 않았음.

### 수정 내용
- `Front/src/types/youtube.d.ts` (신규) — `window.YT`, `window.onYouTubeIframeAPIReady`
  전역 타입 선언 (`tosspayments.d.ts`와 동일한 ambient `interface Window` 병합 패턴)
- `Front/src/pages/LessonPlayerPage.tsx`
  - 동작하지 않던 `window.addEventListener('message', ...)` 기반 종료 감지 로직 제거
  - `https://www.youtube.com/iframe_api` 스크립트를 최초 1회 로드하는 `useEffect` 추가
  - 유튜브 강의일 때 `new YT.Player('yt-iframe-player', { events: { onStateChange } })`를
    생성하여 `event.data === YT.PlayerState.ENDED`(영상 종료)일 때 기존
    `handleVideoEndedRef.current(lectureId)`(`completeLecture` API 호출)를 그대로 호출
  - iframe에 `id="yt-iframe-player"` 추가, 강의 전환/언마운트 시 `player.destroy()`로 정리

### 검증
`npx tsc --noEmit`, `npm run build` 통과 확인. 백엔드 `EnrollmentService.completeLecture()`,
`Enrollment.updateProgress()`, `Course.lectureCount` 동기화(`LectureService.syncLectureCount()`)는
코드 검토 결과 정상이며, 업로드형 영상의 `<video onEnded>` 흐름도 기존과 동일하게
정상 동작함을 확인.

## BUG-006: 토스 결제 성공 후에도 "결제 확인 실패" 화면이 표시되는 문제

### 발생일
2026-06-13

### 증상
토스 결제창에서 결제를 정상적으로 완료하고 `/payment/success`로 리다이렉트되면,
백엔드 로그상으로는 `POST /api/payments/toss/confirm`이 200 OK(`status=COMPLETED`)로
정상 처리되었음에도 프론트엔드에는 "결제 확인 실패" 화면이 표시됨.

### 원인
`Front/src/pages/PaymentSuccessPage.tsx`는 `useEffect` 내부에서 `confirmTossPayment()`를
직접 호출하는데, `Front/src/main.tsx`에서 React 18 `<StrictMode>`를 사용 중이라 개발
모드에서는 마운트 시 effect가 두 번(mount → cleanup → mount) 실행됨. 그 결과 동일한
`paymentKey`/`orderId`/`amount`로 `/api/payments/toss/confirm`이 두 번 호출됨.

- 첫 번째 호출: Toss API 승인 성공 → `Payment.status`를 `PENDING` → `COMPLETED`로 변경,
  `Enrollment` 생성, 200 OK 응답
- 두 번째 호출: `PaymentService.confirmToss()`의 `payment.getStatus() != PENDING` 검사에
  걸려 `PAYMENT_ALREADY_DONE`(409, "이미 완료된 결제입니다.") 에러 응답

`PaymentSuccessPage.tsx`는 두 응답을 모두 받아 첫 번째 호출의 결과로 `setResult`(성공),
두 번째 호출의 결과로 `setError`(실패)를 각각 호출했는데, 최종 렌더링 조건이
`if (error || !result)`였기 때문에 `result`가 정상적으로 설정되어 있어도 나중에
`error`가 set되면 무조건 실패 화면이 표시되었음.

### 수정 내용
- `Front/src/pages/PaymentSuccessPage.tsx` — `useRef`로 `requestedRef` 가드를 추가하여
  `useEffect`가 두 번 실행되더라도 `confirmTossPayment()` API 호출이 한 번만 발생하도록 수정

### 검증
`npx tsc --noEmit`, `npm run build` 통과 확인.

## BUG-007: 강의 완료(진도율) 처리 시 lecture_index 컬럼 오류로 500 발생

### 발생일
2026-06-13

### 증상
유튜브 강의를 끝까지 재생하면(BUG-005 수정으로 정상적으로 호출됨)
`POST /api/enrollments/{courseId}/complete-lecture/{lectureId}`가 500 오류를 반환함.

```
HHH000247: ErrorCode: 1364, SQLState: HY000
Field 'lecture_index' doesn't have a default value
insert into lecture_completions (completed_at,enrollment_id,lecture_id) values (?,?,?)
```

### 원인
`lecture_completions` 테이블에 과거 설계(레슨을 `lecture_id`가 아닌 `lecture_index`로
추적하던 시절)에서 생성된 `lecture_index INT NOT NULL`(기본값 없음) 컬럼과
`UNIQUE KEY (enrollment_id, lecture_index)`가 남아있었음.

`LectureCompletion` 엔티티는 이미 `lecture_id` 기반으로 변경되어 있고
(`@Table(uniqueConstraints = @UniqueConstraint(columnNames = {"enrollment_id", "lecture_id"}))`),
Hibernate가 생성하는 INSERT문에는 `completed_at`, `enrollment_id`, `lecture_id`만 포함됨.
`ddl-auto: update`는 더 이상 쓰이지 않는 컬럼을 제거하지 않으므로, 테이블에는 옛
`lecture_index` 컬럼이 `NOT NULL` 상태로 그대로 남아 있었고, INSERT문에 값이 없어
MySQL strict mode에서 `Field 'lecture_index' doesn't have a default value` 오류가 발생함.
(BUG-002와 동일한 유형의 `ddl-auto: update` 스키마 드리프트)

### 수정 내용
운영 DB(`unggae` 스키마)의 `lecture_completions` 테이블에 직접 SQL 마이그레이션 적용
(기존 데이터 없음 확인 후 적용).

```sql
ALTER TABLE lecture_completions
  DROP INDEX `UK1ub0xnqvg69ao7td7i0apk9dn`,
  DROP COLUMN lecture_index;
```

### 검증
`SHOW CREATE TABLE lecture_completions`로 컬럼/제약이 엔티티 정의
(`id`, `completed_at`, `enrollment_id`, `lecture_id`, `UNIQUE(enrollment_id, lecture_id)`)와
일치함을 확인. 엔티티/코드 변경 없이 DB 스키마만 수정했으므로 백엔드 재시작 없이
바로 정상 동작 예상 — 실제 강의 화면에서 영상을 끝까지 재생해 진도율이 갱신되는지
재확인 필요.

## UI 개선: 결제 페이지(PaymentPage) 결제수단 선택 UI 도입

BUG는 아니지만 BUG-002 수정과 함께 진행한 UI 개선 사항.

- `Front/src/pages/PaymentPage.tsx` — 단순 "결제하기" 버튼 1개였던 화면을,
  주문 상품 정보 + 결제수단 선택(카카오페이/토스페이/네이버페이/카드/계좌이체/휴대폰)
  + 약관 동의 + 결제 금액 요약으로 구성된 일반적인 PG 결제창 형태로 재구성.
- 결제수단은 UI 선택 항목일 뿐이며, 실제 결제 처리(`preparePayment` → `confirmMockPayment`)는
  선택값과 무관하게 동일한 mock 흐름으로 동작함.
