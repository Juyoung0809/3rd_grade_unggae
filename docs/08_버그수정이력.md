## BUG-001: 유료 강의 수강신청 시 결제 페이지로 이동하지 않는 문제

### 발생일
2026-06-11

### 증상
유료 강의 상세 페이지에서 "수강신청" 버튼을 클릭하면 결제 페이지로 이동하지 않고,
"유료 강의는 결제 후 수강신청이 가능합니다" 라는 alert 팝업만 뜨고 그대로 멈춤.

### 원인
`Front/src/pages/CourseDetailPage.tsx`의 `handleEnroll()`이 강의 가격과 무관하게
`enroll()` API(`/api/enrollments`)를 직접 호출하고 있었음. 백엔드의
`EnrollmentService.enroll()`은 `course.getPrice() > 0`이면 `PAYMENT_REQUIRED` 에러를 던지므로,
프론트는 이 에러 메시지를 alert으로만 띄우고 결제 흐름으로 연결하지 않았음.

### 수정 내용
`handleEnroll()`에서 `course.price > 0`인 경우 `enroll()`을 호출하지 않고
`/payment/:courseId`(결제 페이지)로 라우팅하도록 분기 추가. 무료 강의는 기존처럼
`enroll()`을 직접 호출하여 즉시 수강 등록되도록 유지.

- `Front/src/pages/CourseDetailPage.tsx` — `handleEnroll()` 수정

### 검증
유료 강의 상세 페이지에서 "수강신청" 클릭 시 `/payment/:courseId`로 정상 이동하는 것을 확인.

## BUG-002: 결제 진행 시 /api/payments/prepare 500 서버 오류

### 발생일
2026-06-11

### 증상
결제 페이지에서 "결제하기"를 누르면 `POST /api/payments/prepare` 호출이
`500 INTERNAL_SERVER_ERROR` ("서버 오류가 발생했습니다.")를 반환하며 결제가 진행되지 않음.

### 원인
DB의 `payments` 테이블 스키마가 `Payment` 엔티티 정의와 어긋나 있었음
(과거 설계 당시 만든 테이블이 엔티티 변경 후 마이그레이션되지 않음, `ddl-auto: update`는
컬럼 타입/ENUM 값/NOT NULL 변경이나 컬럼 추가를 자동으로 반영하지 못함).

- `method` ENUM이 `('CARD','FREE')`로 되어 있었으나 엔티티는 `FREE`/`TOSS` 값을 기대
- `status` ENUM이 `('COMPLETED','REFUNDED')`로 되어 있었으나 엔티티는
  `PENDING`/`COMPLETED`/`FAILED`/`REFUNDED` 값을 기대
- `paid_at` 컬럼이 `NOT NULL`이었으나, `PENDING` 상태의 결제는 `paidAt`이 `null`이어야 함
- `created_at` 컬럼이 테이블에 아예 존재하지 않음
  (엔티티는 `@Column(name = "created_at", nullable = false)` 필수)

### 수정 내용
운영 DB(`unggae` 스키마)의 `payments` 테이블에 직접 SQL 마이그레이션 적용.

```sql
-- ENUM 확장 후 기존 데이터 변환, 다시 축소
ALTER TABLE payments MODIFY COLUMN method ENUM('CARD','FREE','TOSS') NOT NULL;
ALTER TABLE payments MODIFY COLUMN status ENUM('PENDING','COMPLETED','FAILED','REFUNDED') NOT NULL;
ALTER TABLE payments MODIFY COLUMN paid_at DATETIME(6) NULL;
UPDATE payments SET method = 'TOSS' WHERE method = 'CARD';
ALTER TABLE payments MODIFY COLUMN method ENUM('FREE','TOSS') NOT NULL;

-- created_at 컬럼 추가 및 백필
ALTER TABLE payments ADD COLUMN created_at DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6);
UPDATE payments SET created_at = paid_at WHERE paid_at IS NOT NULL;
```

### 검증
`@SpringBootTest` 기반 임시 디버그 테스트와 curl을 통해
`prepare` → `mock-confirm` → `my-payments` → `my-enrollments` 흐름을 모두 200 OK로 확인.
결제 완료 시 `Enrollment`가 정상 생성되고 결제 내역 조회도 정상 동작함을 검증 후,
테스트 데이터 및 임시 디버그 테스트 파일은 모두 삭제함.

## BUG-003: 결제 요청 실패 시 백엔드 로그에 아무 기록도 남지 않는 문제

### 발생일
2026-06-11

### 증상
결제 모달에서 "다음"을 눌러 결제를 진행하면 "결제 중 오류가 발생했습니다."
(프론트엔드의 일반 fallback 메시지)만 표시됨. 그런데 `Back/logs/unggae.log`에는
`/api/payments/*` 요청이 단 한 건도 기록되지 않아, 요청이 실패하는 지점을
특정할 수 없었음.

### 원인
`RequestLoggingFilter`가 `@Order(1)`로 등록되어 있었는데, Spring Security의
`FilterChainProxy`는 `Ordered.HIGHEST_PRECEDENCE + 100` (훨씬 낮은 값 = 더 먼저 실행)
순서로 등록되어 항상 먼저 실행됨. `/api/payments/**`는 `anyRequest().authenticated()`
규칙에 걸리는데, 액세스 토큰이 없거나 만료된 상태로 요청하면 Spring Security가
`AuthorizationFilter` 단계에서 401/403으로 즉시 응답을 커밋해버리고, 그 뒤에 있는
`RequestLoggingFilter`까지 요청이 도달하지 못해 아무 로그도 남지 않았음.

또한 이때 응답 바디가 `ApiResponse` JSON 형식이 아니라 비어 있어서, 프론트엔드의
`err.response?.data?.message`가 `undefined`가 되어 항상 일반 fallback 메시지
("결제 중 오류가 발생했습니다.")만 표시되었음.

### 수정 내용
- `Back/src/main/java/juyoung/unggae/common/filter/RequestLoggingFilter.java`
  — `@Order(1)` → `@Order(Ordered.HIGHEST_PRECEDENCE)`로 변경하여 Spring Security
  필터 체인보다 먼저 실행되도록 수정. 이제 인증 실패로 거부된 요청도 `[REQ]`/`[RES]`
  로그(상태코드 포함)가 남음.
- `Back/src/main/java/juyoung/unggae/common/security/SecurityResponseHandler.java` (신규)
  — `AuthenticationEntryPoint`/`AccessDeniedHandler` 구현체 추가. 인증/인가 실패 시
  WARN 로그를 남기고, `ApiResponse` 형식의 JSON(`{"code":"UNAUTHORIZED", "message":"로그인이 필요합니다.", "data":null}` 등)을
  401/403 상태코드와 함께 반환.
- `Back/src/main/java/juyoung/unggae/common/security/SecurityConfig.java`
  — `.exceptionHandling()`에 `SecurityResponseHandler`를 `authenticationEntryPoint`/
  `accessDeniedHandler`로 등록.
- `Back/src/main/java/juyoung/unggae/common/response/ErrorCode.java`
  — `UNAUTHORIZED`(401, "로그인이 필요합니다."), `FORBIDDEN`(403, "접근 권한이 없습니다.") 추가.

### 검증
백엔드 재시작 후, 토큰 없이 `curl -X POST /api/payments/prepare`로 호출하여
- 응답: `401 {"code":"UNAUTHORIZED","message":"로그인이 필요합니다.","data":null}`
- `unggae.log`에 `[REQ] POST /api/payments/prepare` → `[WARN] 인증 실패 (401)` →
  `[RES] POST /api/payments/prepare → 401`이 모두 기록됨을 확인.

이제 결제 요청이 실패하면 (1) 백엔드 로그에 항상 추적 가능한 기록이 남고,
(2) 토큰 만료/누락 시 프론트엔드에 "로그인이 필요합니다."라는 명확한 메시지가
표시되어, 일반 fallback 메시지로 원인을 알 수 없던 문제가 해결됨.

## UI 개선: 결제 페이지(PaymentPage) 결제수단 선택 UI 도입

BUG는 아니지만 BUG-002 수정과 함께 진행한 UI 개선 사항.

- `Front/src/pages/PaymentPage.tsx` — 단순 "결제하기" 버튼 1개였던 화면을,
  주문 상품 정보 + 결제수단 선택(카카오페이/토스페이/네이버페이/카드/계좌이체/휴대폰)
  + 약관 동의 + 결제 금액 요약으로 구성된 일반적인 PG 결제창 형태로 재구성.
- 결제수단은 UI 선택 항목일 뿐이며, 실제 결제 처리(`preparePayment` → `confirmMockPayment`)는
  선택값과 무관하게 동일한 mock 흐름으로 동작함.
